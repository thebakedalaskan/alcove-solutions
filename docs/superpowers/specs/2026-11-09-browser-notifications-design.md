# Browser notifications

Finish #88 in its own issue branch. Notifications operate while Alcove remains open; no Web Push or delivery after every tab closes is promised.

- Extend the existing sealed NotificationPrefs model with an explicit master and call categories. Existing stored profiles default the missing master to true, preserving their browser permission and existing category choices; new accounts explicitly start master-off. New private/reply/mention/hand/question/admission/timer categories start off. Sounds remain independently controlled by SoundPreferences. OS notifications are silent; the existing sound graph owns audible cues.
- Settings and in-call controls show current support/permission, a deliberate Enable browser notifications action, global/category switches, clear denied/revoked/unsupported guidance and persistent in-app alternatives. Only that action may request browser permission. Signed-out guests use the same validated preference shape locally, starting off.
- Add a minimal immutable, content-free CallSession notification candidate snapshot, derived only from currently authorized call, MLS chat, direct and thread snapshots. Stable event IDs identify exact original audience/room/thread/action targets. No new server authority or stored private content is introduced. Real HTTP integration flows validate event selection, current audiences, reconciliation and lifecycle.
- One browser delivery owner reconciles outstanding candidates, closes handled/revoked/removed alerts, deduplicates across tabs and reconnects, groups bursts and discards stale alerts. Atomic receipts and focused-view presence contain opaque IDs and timestamps only. Async delivery is fenced by account/context generation, current preferences, permission and current candidate presence.
- Every OS title/body is generic. No names, titles, messages, notes, workspace details, secrets or call passes enter OS previews or logs. Clicking focuses an existing Alcove tab where possible and passes an exact typed intent. The active session checks original room, generation, recipient and target availability before opening protected content; an unavailable destination explains why without retargeting.
- Keep existing call reminders, notes, document tags and follow-ups, but make their previews generic and their delivery obey the same global lifecycle, preference and reconciliation rules. Reuse the native UI and update Storybook states/journeys for permission, categories, foreground/background, grouping, failures and destinations.

Stored profile fields are additive with defaults; existing encryption headers and key labels stay unchanged. Browser-only receipt and guest preference schemas remain bounded and contain no content. No SQL migration is planned. User/root approved implementation scope; final integration review, checks and release are coordinated by root.
