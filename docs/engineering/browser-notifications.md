# Browser notifications

Browser alerts are an optional complement to unread chat, reply counts, People and timers. Alcove must remain open in at least one tab or window. There is no Web Push provider, server subscription or delivery guarantee after every tab closes. Browsers and operating systems decide whether a permitted alert appears as a banner or in their notification centre. Some mobile browsers require an installed web app or do not support these APIs; the controls explain when notifications are unavailable.

Settings → Notifications and, in a call, More → Settings → Notifications use the same account preferences. Each thing that can reach someone has one Alert tick in `NotificationPrefs`, which lets it reach them from the browser while Alcove isn't in front, once the master (`enabled`) is on and the browser allows it. Two also gate something on screen: a call's reply and mention toasts follow `replies` and `chatMentions` whatever the browser's permission; every other tick gates only the browser. Guests deliberately opt in using the same validated shape in their `alcove.guest.notifications` local preference. Only the browser notifications control in Settings requests browser permission. Denied/revoked permission is observed through the Permissions API where supported, plus focus/visibility refresh; there is no automatic repeat prompt. Sounds are separate ticks. OS alerts are always silent; the existing sound owner remains the only audible cue.

## Recipients and freshness

`CallSession.notifications` is a content-free, immutable projection of the current authenticated call, MLS and direct-message snapshots. It grants no new access. A successful current synchronization authorizes it; API/MLS failures suspend it. Private events require the exact current recipient, peer, generation and room. Admission events require the current host; notes requests require the organizer. Questions and room messages follow the source snapshots' existing audience. Thread replies are relevant only to authors and participants; a mention takes one room-message category and a private mention remains one private-message event.

The projection and browser observe all confirmed incoming message IDs, including irrelevant messages and disabled categories. A first reply, reading, enabling a category or reconnecting cannot turn an already observed source into a fresh event. Raw unread destinations remain available for navigation, separately from the two-minute delivery window. Initial synchronization is a baseline, not a backlog. Current hands, questions and requests disappear when handled; admission delivery expires after thirty minutes. Timer warnings/expiry have distinct stable event IDs and disappear when the timer pauses or stops.

Focused relevant views publish only opaque account/context IDs through an expiring BroadcastChannel/localStorage presence record. The OS delivery owner consumes observed events without showing another alert. The lookup itself is read-only and never schedules its own reconciliation. Presence expires after 6.5 seconds; abandoned rows are removed. Call presence is for the visible main call; the floating picture alone does not expose a conversation.

## Delivery and cleanup

All OS strings are defined in `features/shell/notification-delivery.ts`; sources cannot provide preview text. Names, messages, titles, workspace details, keys and passes never enter a notification. Data contains opaque destination IDs, the public call code when needed, account ID and a random delivery instance. It contains no credentials or access-bearing invitation URL. Logs contain category/count or failure state only.

Each source groups current events by category into one stable OS tag. Atomic IndexedDB read/write claims deduplicate event IDs across simultaneous tabs even without Web Locks. Short pending leases recover abandoned delivery; shown receipts remain only until the event's delivery expiry, with a bounded store. Existing `alcove.notified.<ownerId>` receipt keys remain readable. Sign-out clears browser receipts and outstanding OS notifications. A late async completion rechecks owner, permission, original context, current event, expiry and focused presence. Worker cleanup closes its exact random delivery instance so an older completion cannot close a replacement.

Read/withdrawn/handled events reconcile the OS handle where the browser supports closing it. Master/category changes propagate as explicit leaf patches with the original opaque account-generation fence. Pending and terminal messages retain the command nonce; each receiver accepts a confirmation or rollback only for leaves still owned by that nonce. Hints stay separate from the confirmed query projection, expire with an active notification after90 seconds, and never inject a whole snapshot into it. Terminal messages refresh that projection, and30-second account polling recovers changes from other devices. Disable/revoke cleanup checks the latest intent after browser awaits. No notification is the sole record of pending activity. Delivery failure leaves those persistent in-app indicators and explains the failure with a generic toast.

Clicks focus the same account's existing tab, preferring the exact original call connection. The page refreshes session and call access before opening the existing chat/thread, exact focused action row, or timer. A removed/handled destination says it is unavailable. An original private session that ended is never reconstructed in another connection. A new window receives its intent only after the navigation listener is ready, without adding it to a URL or persistent storage. Normal leave/recording guards still apply to page navigation.

## Rings

Someone signed in, with browser notifications on and rings ticked, who is rung while no Alcove tab of theirs is focused gets one browser alert per ring: “Someone is calling you” / “Open Alcove to answer.”, naming nobody and no call. `features/calls/ringing/RingAlert.ts` is its source: each tab's `RingHost` registers the rings it shows a card for with the same delivery owner, gated in one `allowed` check by the master, the browser's permission, the account fence and `ringing`. An alert's key is the ring's ID and end (`ring:<id>:<expiresAt>`), so a ring that comes back after In 5 minutes is a new ring, and the atomic receipts show each ring once across tabs, reloads and new tabs. A focused tab of the account publishes the opaque `<ownerId>:rings` view, so nothing shows while a card is in front, and a ring seen there while alerts are on never turns into an alert later. The alert closes when the ring ends (answered in any tab, declined, stopped by the organizer, run out) or when Alcove comes to the front. It leads to `{ to: 'ring' }`: the worker focuses the account's last-used window, preferring no path, and the page, after its usual account check, stays where it is, with the card. The ring's sound stays with `RingSound.ts`. With no Alcove tab open there is still no ring, as there is no Web Push.

## Stored-data upgrade

There is no new SQL migration or sealed record kind. `NotificationPrefs` adds defaulted fields: old sealed profiles preserve explicit browser permission and existing categories (`enabled` defaults to true for those profiles); new accounts explicitly start with the browser master false. New call categories default false, except as folded below.

The call's own reply and mention toast switches (`replyAlerts`, `mentionAlerts`) are gone. Stored profiles and guest records fold them into `replies` and `chatMentions` as the stored schema reads them (`replies || replyAlerts`, `chatMentions || mentionAlerts`, only where the old field is present), so a toast that was on stays on, and that category's browser alert is allowed too while the master is on. A record from before both reads `replies` and `chatMentions` as true, as its toasts were. `ringing` reads as true. The next save writes the current shape without the old fields; the input schema has no fold and requires `ringing`, so a tab still running the previous release can't save a notification group (400) until it reloads. A guest's switches were kept under keys of their own (`alcove.guest.reply-alerts`, `alcove.guest.mention-alerts`), and its record's `replyAlerts` and `mentionAlerts` were only ever the defaults, so `lib/notification-preferences.ts` reads those keys once (on when absent or unreadable) in place of the record's copies, or over the defaults with no record, folds them the same way, writes the record back and removes the keys. New accounts and guests start with the master off and every Alert on except new questions and follow-ups. Incoming `PreferencesPatchSchema` requests must supply complete current notification and sound groups; omitted fields are rejected before any preference changes. Stored defaults continue to upgrade previous sealed profiles. This prevents an already-open older client’s group request from opting into the new browser master through stored-record defaults. Browser-only receipts hold no message content and are physically cleared on sign-out.

## Verification

Real HTTP integration flows cover new-account and prior-profile defaults, account isolation, host admission, read/withdrawal reconciliation, recipient-only private messages, relevant room threads, all-message freshness baselines, whole-API outage/recovery, notes requests, presenter/board timers and breakout boundaries. They use real Postgres/object storage and the public HTTP client. Browser-specific behavior is checked manually; Storybook journeys demonstrate it and contain no assertions. The native browser story uses the real permission/Notification APIs with synthetic media and a stand-in call, and reports public creation/show/error/close events without changing product behavior.


Manual development verification on Chrome: the explicit real permission prompt, native `show` events with generic silent copy, worker `showNotification` acceptance/replacement/close, focused-view suppression, keyboard activation,390px/wide layouts and both themes were observed. Two explicit shared-clock fixture tabs received the same8 authorized sources: the first created8 records across6 grouped categories and the second created none. Enable/disable synchronized, and re-enable did not replay old sources. The real native click callback was invoked through the separate Storybook control and opened the original private conversation/exact question; handled-target feedback was observed. An OS notification-centre click and new-window worker handoff were not observed in this environment. Test alerts were closed, the development permission returned to Ask, both masters were Off, the worker was unregistered and viewport/focus overrides were restored.

Final combined validation after integrating main’s private messaging, threads, mentions and immutable preference commands:226/226 real HTTP flows passed across9 affected suites in311.19 seconds; all7 package type checks,3 builds and policy guards passed. Independent delivery/preference-lifecycle and required-input/stored-upgrade reviews were clear. A two-tab manual overlapping-choice scenario showed a refused first leaf rolling back in both views while the later independent leaf stayed selected. With its writer closed and masterOff, a live transient hint expired after its90-second lease and the remaining view rerendered its separate fixture’s authoritative baseline without interaction.
