# Call chat mentions

The room and private composer share selected stable participant identities and UTF-16 text spans. Search shows an account address or a guest connection identity to distinguish matching names; private audience choices also distinguish matching names. Editing selected words removes that selection. Each room, original private pair and thread keeps its own draft and spans.

`calls/chat-mentions.ts` owns validation shared by MLS and direct text. Both paths trim outgoing text and rebase selected spans together. Room identities must belong to the readable MLS room. Direct identities must be exactly one of the two original connections, and the receiver repeats this check after authenticated decryption, before acknowledging delivery. A selected name never grants membership or changes a thread audience. Metadata stays inside the existing encrypted text envelope, with no cleartext routing, logs, URLs or shared-note/export data.

The direct LiveStore computes `unreadMentions` from confirmed delivered incoming unread messages. Authorized retained decrypted history keeps its mention count after the other participant leaves, a room move or a new generation. It remains readable through its original conversation. Transport authorization loss suspends history and counts until the same connection is rechecked; removal and call end clear both. Reload/replacement connections inherit no private keys or history. Reading the visible addressed span clears the original receipt, independently of whether that row can still produce fresh alerts.

Local mention toasts contain only “Someone mentioned you in your call.” Their action rechecks the exact call, connection, generation, room and readable destination before opening its message/thread. They never take focus themselves. Fresh room/private eligibility requires a current audience, a confirmed incoming message and a recent observation. Every confirmed incoming ID is baselined continuously even when a preference is off, so read, preference or relevance changes cannot turn history into a fresh event. Reconnects and scope changes start a new baseline.

The existing sound scheduler handles mention cues, master/category volume, quiet mode, output routing and one event key per message. A self-addressed mention takes precedence over a reply cue. `notifications.mentionAlerts` controls the generic local toast independently of `sounds.mentions` and optional browser notifications. Guests keep these local visual choices in the same guest preference owner; account choices remain in the sealed owner profile. Browser notifications are coordinated separately in #88. Its adapter must keep one private-message candidate for a private mention, including a thread reply.

## Stored data upgrade and verification

No SQL migration or key/header change is needed. Older encrypted private/MLS text without `mentions` reads as `[]`; older sealed profiles acquire `sounds.mentions = true` and `notifications.mentionAlerts = true` from defaults. Existing choices survive, and the next save writes the current shape. Pair-bound retry retains the exact original envelope and ID, so an ambiguous acknowledgement cannot create duplicate delivered rows or alerts.

Real HTTP flows cover matching names, whitespace spans, room/private nested replies, self-mentions, forged recipient spans, malicious encrypted metadata, failed and ambiguous sends, authorization loss, departure/room-return reads, replacement connections, cross-owner profile choices, storage/log canaries and physical cleanup. Storybook records picker, selected, confirmed, failed/retry, matching-name, retained-history and generic-alert states and journey 6.32 in both themes and phone/wide layouts. These are demonstrations, without a browser test runner or component assertions.
